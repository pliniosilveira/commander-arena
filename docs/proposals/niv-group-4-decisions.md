# Niv-Mizzet deck, group 4: repeatable modes (provisional decision numbers)

Provisional numbers D-1000 to D-1009: the integrator renumbers them into `docs/DECISIONS.md` and replaces them in the code comments. The owner approved building repeatable modes as a general feature (docs/proposals/niv-mizzet-owner-decisions.md, section 3, and D-317); Fiery Confluence (issue 25, acceptance card of the golden corpus) is the first card that needs it. The feature is documented in `docs/MECHANICS.md` ("Repeatable modes") and `docs/RULES_COVERAGE.md`.

## D-1000: Repeatable modes: `ModeChoice.repeatable` and a choice of modes that is a multiset (2026-11-12)

- Context: "Choose three. You may choose the same mode more than once." (CR 700.2d) lets the controller choose a mode several times; "If a particular mode is chosen multiple times, the spell is treated as if that mode appeared that many times in sequence." D-114 built `legalModeSets` for sets of distinct modes and listed "the same mode twice" as not built. The owner decided (D-317) that a card that is common enough is built as a general feature, not for one card.
- Decision: `ModeChoice.repeatable?: true` (`ast/types.ts`). The modes chosen stay an array of mode indices in printed order, now with repeats allowed when the text says so (`[0, 0, 2]`): `StackData.chosenModes`, the `chooseModes` action and the `modesChosen` event keep their shapes, so no new decision kind, no new action kind and no new event kind. `ChooseModesDecision.repeatable` (present only when true) says the `sets` are multisets and that `max` may be more than the number of modes. `legalModeSets` lists, for a repeatable choice, every multiset of between `min` and `max` of the modes that can be chosen (fewest first, then lexicographic: a mode may be taken again), `isLegalModeSet` compares the sorted array with the listed sets (the list says whether a repeat is allowed), `modeLimit` has no widening for a repeatable choice, and the invariant "chosen modes are in printed order" is non-strict for a repeatable choice. The instances of a mode run one after the other in printed order of the modes (CR 608.2c, 700.2d).
- Alternatives: A counted map `{ mode: count }` in the state and the action: rejected, every consumer (the view, the log, the AI, the copy code, the tests) already reads an array of indices, and a sorted multiset is the same information. A separate `repeatableModes` field on the spell text instead of a flag on the choice: rejected, the flag is a property of how many modes are chosen and the choice already has `maxIf` and `notRepeatedThisTurn` beside it. Making the number of choices a list of an enumeration without a bound: rejected, the engine lists every legal answer (D-114), so the number of multisets is bounded (D-1002).
- Consequences: A mode chosen once is exactly what it was, so no old text, action log or digest changes (the digest of 6 precon games from `tools/perf/precon-digest.ts` is identical before and after, and the soak games of every older style are unchanged because the new cards are kept out of the generic pools, D-1005). Escalate (D-145) counts the instances (`chosenModes.length`) as it counts modes, which is what a repeatable Escalate card would need; no such card is supported or tested yet.

## D-1001: Every instance of a mode has target slots of its own (2026-11-12)

- Context: A single slot for all instances of a targeted mode would be wrong when there are fewer targets than instances (CR 700.2d: the same target may be chosen for each, or different ones; CR 601.2c: targets are chosen for every instance of the word "target"), and a slot of the whole spell would also make "destroy target artifact" three times with two artifacts a different spell. The slot ids of a mode are unique across the modes, and effects name their slots by id.
- Decision: The first instance of a mode keeps its slots' ids; the later ones get `<id>#2`, `<id>#3`, ... (`instanceId` in `rules/modes.ts`; `baseSpecId`, exported from the engine, undoes it for a reader that wants the slot of the text). `chosenModeSpecs` returns the slots of every instance in printed order, each a copy of the mode's `TargetSpec` with its own id (and `differentFrom` renamed within the instance); `chosenEffect` rewrites the `{ kind: 'target', id }` nodes of the instance's effect to the instance's ids (`instanceEffect`), so the resolution reads each instance's own targets from `chosenTargets` with the code it always had (`stillLegalTargets`, CR 608.2b: an instance whose target is gone does nothing and the spell fizzles only when all its targets are illegal). `TargetChoiceSpec.instance` (present from the second instance on) says which instance a slot is, for the web prompt. A slot never takes the same target twice (CR 601.2c), but two slots may take the same one. `targetChoiceSpecs` takes a map of `{ mode, instance }` (`specModes`). The same code serves a spell, an activated ability, a triggered ability and the copy of a modal spell (the copy keeps `chosenModes` and `chosenTargets`, CR 707.10 and 700.2g, and its new-targets question lists the slots of every instance with `forCopy`). A triggered ability whose slots are all forced (one legal target for each) takes them without asking (CR 603.3d), as before.
- Alternatives: One slot with a larger `max` for all instances of a mode: rejected, it cannot express two instances aimed at the same target with fewer targets than instances, and it changes `targets` decisions that the web and the AI read one slot at a time. Rewriting the effect text when the card is imported (copies of the mode in the AST): rejected, the number of instances is the player's choice as the spell is cast. A different id syntax (`id@2`): `#` was chosen because no id the parser or the fixtures write has one; the validator refuses an id with `#` in a repeatable choice.
- Consequences: Old spells and abilities have no instance slot: their slot ids, decisions and events are unchanged. `legal-actions.ts` lists the combinations of targets of a decision that has instance slots up to 500 (as `choosePermanent` lists its choices, `MAX_LISTED_CHOICES`), because three slots of ten artifacts is a thousand combinations; any legal answer is accepted all the same. Decisions without instance slots are listed in full as before.

## D-1002: What a repeatable choice may say (2026-11-12)

- Context: The validator must refuse what the engine cannot run or list (D-114: "the engine lists every legal choice").
- Decision: `validateCard` accepts `chooseModes { min, max, repeatable: true }` with `0 <= min <= max`, `max >= 1`, and `max` may be more than the number of modes; `min` 0 is "Choose up to N. You may choose the same mode more than once." (an empty choice is a legal answer for a spell and an activated ability: it resolves and does nothing; a triggered ability with no mode chosen is removed from the stack, CR 700.2b, which the engine does not run, so the validator refuses `min` 0 on a triggered ability and such a card stays unsupported). A repeatable choice has no `maxIf` and no `notRepeatedThisTurn`. The number of multisets between `min` and `max` of the modes may not exceed `MAX_REPEATABLE_SETS` (2000, `ast/validate-modes.ts`). A target id with `#` is refused in a repeatable choice. The 2 to 8 modes limit (`MAX_MODES`) is unchanged. A choice that is not repeatable is validated as before (1 <= min <= max <= number of modes).
- Alternatives: No bound on the number of sets: rejected, the action list and the decision would grow without limit. A lower bound on `min`: "up to" is a real wording and costs one case.
- Consequences: Eight modes and up to five choices (1286 multisets) are allowed, ten choices of eight modes are refused with the card unsupported, honestly, rather than half run.

## D-1003: The parser reads the header of a repeatable choice (2026-11-12)

- Context: The Oracle text of Fiery Confluence is "Choose three. You may choose the same mode more than once." followed by bullets, with no dash after the header; the bullets already parsed. `modal.choose` reads only the dash forms.
- Decision: The rule `modal.choose-repeatable` (`parser/rules/modal/index.ts`) reads `Choose <two..ten>. You may choose the same mode more than once.` and `Choose up to <two..ten>. You may choose the same mode more than once.`, as the lead line of a spell, a triggered ability (after "When ~ enters,") or an activated ability (after the cost); the engine runs "up to" on a spell and an activated ability only (D-1002). `IrModeChoice.repeatable` carries it and `lowerModes` writes `chooseModes { min, max, repeatable: true }` (`min` is the number, or 0 after "up to"); the lowering no longer requires `max <= number of bullets` for a repeatable choice. Not read: "Choose one. You may ...", "Choose up to one. You may ...", "Choose X ...", "Choose any number ...", a bare "Choose three —", a number above ten. `PARSER_VERSION` is not changed here (the integrator does it once for the group).
- Alternatives: Reading the sentence "You may choose the same mode more than once." as a separate rule that modifies any header: rejected, the number word is part of the same sentence ("Choose three.") and a header that is not read must not leave a half-read modal.
- Consequences: Fiery Confluence is supported from the grammar alone (no override). The golden snapshot (`golden.expected.json`) changes for that one card (unsupported to supported, acceptance 226 of 245) and is regenerated by the integrator.

## D-1004: The agents and repeatable modes (2026-11-12)

- Context: The agents answer `chooseModes` with one of the listed sets and `targets` with a legal answer; a repeated mode must not make the opponent waste a whole choice on one artifact.
- Decision: `RandomLegalAgent` picks one of the listed sets, as it did. `CasualAgent` (and `HeuristicAgent`, which uses it for modes) scores a set as the sum of its modes (`chooseModesAnswer`); when `ChooseModesDecision.repeatable` is set, an instance of a mode that names a target scores only while there are targets for it (`worthRepeating`: the opposing creatures for "destroy/damage target creature", the opposing permanents of the type for "target artifact"), so three instances of "destroy target artifact" are worth no more than the artifacts there are; a mode that can go to a player each time (damage to each opponent) is worth every time. `chooseModalTargets` plans a slot of a later instance with the plan of the slot it repeats (`baseSpecId`) and takes other targets than the earlier instances of the same mode when there are others. `isModalText` reads "Choose three" and the other number words.
- Alternatives: Always choosing the best single mode three times: rejected (three destroys of one artifact). Reading the legal targets of each mode in the agent: the agent reads the view, as for X (`casual-x.ts`).
- Consequences: No change for a choice without repeats (each mode appears once, the first instance scores as before). The agent's answer is always a listed set.

## D-1005: Web, soak and the SYNTHETIC pool (2026-11-12)

- Context: The mode picker was checkboxes and radio buttons; the stack and the log said each chosen mode once; the SYNTHETIC cards that test the feature must not change the seeded games of the other styles.
- Decision: The mode dialog shows, for a repeatable choice, a counter for each mode ("-", the count, "+", `data-mode-times`) and the heading of the card ("Choose three. You may choose the same mode more than once."); a digit adds one choice of the mode, Shift and the digit takes one away; Confirm is enabled only for a multiset the engine listed (compared sorted). The targets prompt groups the slots of a mode chosen more than once by the time the mode is chosen ("Mode 3, time 2: Destroy target artifact"). The stack and the log say a mode chosen more than once once with how many times ("Fiery Confluence deals 1 damage to each creature (x2); Destroy target artifact"). The five SYNTHETIC cards of `synthetic-repeatable.ts` have their own deck style `repeatable` in `packages/ai/test/helpers.ts` and are filtered out of the generic pools (as `nivDraw` is), with a soak test `repeatable-modes-games.test.ts` that restates the rules from the cards' texts. The synthetic pool therefore gains five cards, but no existing style draws them: the soak games and the precon digests of every other style are unchanged. No Playwright test was added in this change: the sandbox had no Chromium, and an unrun browser test is not left for the nightly job to find out (the click and key paths are covered by model and static-markup tests, `apps/web/test/modes-repeatable.test.tsx`).
- Alternatives: Adding the cards to the existing `modal` style: rejected, that test restates distinct-mode sets and would change its games.
- Consequences: A browser test of the counters is owed once Chromium is available (`docs/ROADMAP.md`).
