# Hashaton deck, group 7: decisions (provisional numbers D-1130 to D-1139)

Sphinx of the Second Sun (issue 31): "At the beginning of each of your postcombat main phases, there is an additional beginning phase after this phase." The numbers are provisional; the integrator renumbers them into `docs/DECISIONS.md` and the comments of the code.

## D-1130: An additional beginning phase after the postcombat main phase (2026-11-13)
- Context: Sphinx of the Second Sun adds a whole beginning phase (untap, upkeep and draw steps) after each of its controller's postcombat main phases. CR 500.8 says an effect that adds a phase puts it directly after the specified phase, the most recently created one first; CR 500.10 and its Obeka example show that a beginning phase is a phase like any other. The turn structure already had `TurnState.addedPhases` / `addedAfter` for additional combat phases (D-151, D-187), but `AddedPhase.phase` was only `'combat'` and `endStep` always began an added phase with the beginning of combat step.
- Decision: `AddedPhase.phase` is `'combat' | 'beginning'`. A new effect `extraBeginningPhase` (no fields) pushes `{ phase: 'beginning', after: addedAfter ?? phase }` first on `addedPhases`, exactly as `extraCombat` does. `rules/flow.ts` `endStep` begins the first step of the added phase that is next: `untap` for a beginning phase, `beginningOfCombat` for a combat phase. The draw step (the last step of a beginning phase, already in `PHASE_LAST_STEP`) then ends the phase like any other: the next added phase, or else the step after the phase the added phases followed (`FIRST_STEP_AFTER[postcombatMain]` is `end`). The effect is valid (`validateCard`) only in a triggered ability of the `step` trigger `main2` (a new `Scope.postcombatMainTrigger`), the one place where the phase that is going on is known to be the postcombat main phase. Because the added phase is followed by the end phase, and the engine has no second postcombat main phase, the trigger never recurs on its own.
- What the added steps do, all through the ordinary code paths: the untap step phases in the active player's phased-out permanents and untaps their permanents, with no priority (CR 502.1, 502.3, 502.4: `phaseInFor`, `untapPermanent`, stun counters and "doesn't untap" restrictions as in the turn's own untap step); the upkeep and draw steps give priority and the "at the beginning of your upkeep" and "of your draw step" triggers fire again (CR 503, 504, 603.2b); the draw step draws a card (CR 504.1). Per-turn counters (`turnLog`, cards drawn this turn, lands played, spells cast, summoning sickness) are not reset: the turn is the same turn (nothing in the CR resets them in a step).
- The skipped draw of the starting player (CR 103.8a: "skips the draw step of their first turn") applies to the first draw step of turn 1 only. The `draw` case of `beginStep` now skips only when `turn.addedAfter === undefined` (no added phase is going on), so the draw step of an additional beginning phase on turn 1 draws. This changes nothing for any game without an added phase.
- Two Sphinxes: each trigger resolves and adds one phase, so two beginning phases follow the postcombat main phase, one after the other, then the end step (tested). The controller orders the two triggers as for any two simultaneous triggers (CR 603.3b); the order does not matter.
- Alternatives: (a) a general `extraPhase { phase }` effect with the phase as a field: rejected, since an additional combat phase has its own validation scope (attack triggers, `atBeginning`) and the two would share only one line; two effects keep each validation rule exact. (b) Inserting the beginning phase as a copy of the turn's first three steps with a flag for the skipped draw: rejected, the existing `addedPhases` list already has the right order semantics and `endStep` only needed the first step of the phase.
- Consequences: other effects that add a beginning phase ("you get an additional upkeep step", CR 500.10 and 500.10a, which add a beginning phase with only the upkeep step and skip the others) are not built: they need `AddedPhase` to carry the steps it has (see `docs/ROADMAP.md`). A trigger of a different step that adds a beginning phase is refused by `validateCard`, so the card is flagged unsupported rather than guessed at.

## D-1131: What a player sees of an added phase (2026-11-13)
- Context: the step row of the top bar lists the steps of one turn in order, and the pass button names the step a pass leads to. With an added beginning phase the engine goes from Main 2 back to Untap, Upkeep and Draw, then to the End step, which the screen could not tell from the turn's own steps.
- Decision: `GameView` gets two optional fields, present only when set (so every other view and every old snapshot is unchanged): `addedPhase: true` while a phase an effect added to the turn is going on (`phase` says which kind), and `nextAddedPhase: 'beginning' | 'combat'` while one waits. The top bar shows a chip "Extra beginning phase" / "Extra combat phase" while an added phase is going on (`data-added-phase`), the step row still marks the current step (Untap, Upkeep, Draw light up again), and the pass button reads "To Extra Beginning Phase" / "To Extra Combat" at the last step of a phase when one waits, and "To End Step" from the draw step of an added beginning phase (it was "To First Main", wrong there). The words of the ability: "After this phase, there is an additional beginning phase (untap, upkeep and draw steps)" (`ui/decisions/ability-label.ts`).
- Alternatives: marking the added steps in the step row with a second row or a badge on each step: rejected as more machinery than a chip, and the row is a list of the steps of the turn, not a timeline.
- Consequences: the agents see `phase` and `step` as before and need nothing new: no decision kind is added (the Casual, Heuristic and Random agents play turns with one and two Sphinxes in `packages/ai/test/hashaton-g7-agents.test.ts`).
