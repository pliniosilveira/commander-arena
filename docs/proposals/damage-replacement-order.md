# Proposal: the order of replacement and prevention effects on a damage event (CR 616.1)

Status: APPROVED by the owner on 2026-11-02 with all seven recommendations of section 7; steps 1 to 3 of section 6 are BUILT (D-191, merged, `ENGINE_VERSION` 44) and step 4 (Ancient Adamantoise) is BUILT (D-192, D-193, branch `m59-adamantoise`, `ENGINE_VERSION` 45). Differences of step 4 from this text, all in D-192: the default order is prevention (statics, prevent-all, numeric shields) and then the redirections, as the owner decided, not "redirection, then numeric shields" of section 1; a shield that prevents all damage to the player does not ask with a redirection (prevent all first leaves nothing to deal), as in D-191; the shields tracked by the search are all of the game (CR 616.2). It builds the owner's decision of 2026-11-02 recorded in `docs/proposals/damage-redirection.md`: when several replacement or prevention effects apply to one damage event, the affected player chooses the order, one effect at a time, and the engine asks that player. Gap class: S for the one new flow (a question in the middle of dealing damage), but it adds no new decision kind. It is the first slice of Ancient Adamantoise and the generic part that a later move of the "would die" replacements can reuse. Written against engine version 40; this file changed no code.

## Rules (read with `pnpm rule`)

- CR 616.1: "If two or more replacement and/or prevention effects are attempting to modify the way an event affects an object or player, the affected object's controller (or its owner if it has no controller) or the affected player chooses one to apply". The affected player of a damage event is the damaged player, or the controller of the damaged permanent. 616.1a to 616.1d make a self-replacement effect, a "under whose control it enters" effect, a copy effect and a "back face up" effect come first; none of these can modify a damage event, so for damage CR 616.1e applies: any applicable effect may be chosen.
- CR 616.1f: after the chosen effect is applied, the process repeats "taking into account only replacement or prevention effects that would now be applicable", until none is left. CR 616.2: an effect can become applicable because another one modified the event (a redirect makes the shields of the new recipient applicable, and the redirect's own recipient is read again).
- CR 614.5: a replacement effect gets one opportunity to affect an event and the modified events that replace it. CR 614.9: a redirect does nothing if a permanent involved has left the battlefield or is no longer a creature, or a player has left. CR 615.1, 615.6, 615.7: a prevention shield watches for the damage as it would be dealt; prevented damage is never dealt; a "next N" shield is used up by what it prevents. CR 120.3: the results of damage depend on the recipient that finally receives it.

## 1. What is collected, and when the question is skipped

A pure function `damageModifiers(state, event)` (new file `rules/damage-order.ts`) lists the effects that apply to one damage event `{source, to, amount, combat}` as it is now. Today's readers are reused, not copied:

- prevention shields that apply (`applies` in `rules/prevention.ts`, the continuous effects of `preventDamage`);
- static `preventDamageToThis` of the recipient (D-149);
- redirection effects (`redirectDamage`, from the Adamantoise proposal): each static ability on a battlefield permanent whose recipients match `to`, not yet used for this event (CR 614.5), and whose new recipient is legal (CR 614.9).

Each modifier has a stable key: `shield:<continuous effect id>`, `static:<object id>:<ability index>`, `redirect:<object id>:<ability index>`. The function is the only place that decides what applies, so the rule "an effect applies if it would now be applicable" (CR 616.1f) is one function called again after every step.

The question is asked only when the order can change the result. Rule of the engine, in this order:

1. Zero applicable effects: nothing to do. One applicable effect: apply it, no question (CR 616.1 needs two or more).
2. Two or more: explore the order exactly. A pure `settleDamage(state, event, order)` applies the chosen effect, recomputes `damageModifiers` (CR 616.1f), and repeats. A depth-first search over the choices, memoised on the set of effects applied so far, yields every possible final result. The result is canonical: the final recipient, the amount that reaches it, and the shields that remain, listed as (scope, amount left, sources, recipients) without ids or timestamps, so that two equal shields used in either order count as the same result. If every order gives one result, the engine applies the default order (below) and asks nothing. Otherwise it asks.

This is cheap: the number of effects on one event is small (a handful at most; the search is bounded by 2^k states), it runs only when two or more effects apply, and it reads nothing a replay does not already hold. Two "prevent all" shields never ask (neither is used up), a redirect with a shield on the original recipient that prevents everything does ask (shield first: nothing is dealt; redirect first: the Adamantoise takes it), a redirect with one shield on the Adamantoise and one on the original recipient asks. A search cap of 6 effects asks without searching beyond it (never skips a question that should be asked). The alternative, always asking when two or more apply, is simpler and exactly CR 616.1, but it would ask about orders that cannot matter (two Fogs, two equal shields); the exact search costs about 100 lines and is recommended (open question 1).

Default order, used when the result is the same anyway and by agents that need a fixed answer: effects that prevent all damage first, then redirection, then numeric shields oldest first (the owner: "prevent first"). The existing order of `applyShields` is kept as the tail of this order, so existing results do not move.

## 2. The decision

No new decision kind. The question is a `chooseOption` decision (the kind of D-100, D-139, D-175: one pending question, answered by `{kind: 'chooseOption', option}`), with a new purpose `'replacement'`. CR 616.1 asks for one effect at a time ("chooses one to apply", then repeat), which is exactly one `chooseOption` per round. Reusing the kind means `legal-actions.ts`, `RandomLegalAgent`, the scenario DSL (`g.act(seat).chooseOption(...)`), the action log and the replay need no new case; a new kind would have to be added to every `DecisionHandlers` map (web, three agents, testing describe) for no benefit.

Shape (`state/decisions.ts`, `ChooseOptionDecision`):

- `purpose: 'replacement'`; `seat`: the affected player (the damaged player, or the controller of the damaged permanent as it is at that moment of the process, CR 616.1);
- `options`: the keys of the legal modifiers, in the default order (so a fixed answer is `options[0]`);
- `source`, `sourceName`, `sourceOracleText`: the damage source (the existing fields stay required);
- `replacement`: `{ event: {source, sourceName, to, amount, combat}, choices: [{option, object, objectName, kind: 'redirect' | 'prevent', text, then}] }`. `text` is built from the AST by the engine as the other generated texts are ("Prevent the next 3 damage that would be dealt to you", "Deal it to Ancient Adamantoise instead"); `then` is the result if this choice is applied first and the rest follow the default order: `{ to, amount, prevented }`. It is derived from the same search as section 1, so it costs nothing more. It also contains no hidden information.

Legal answers: exactly the keys in `options`; any other string is refused ("Choose one of the effects", `fail(...)` as the other answers do). There is no cancel: damage cannot be taken back. The answer is validated against the recomputed list, never trusted.

Presentation in the web app: reuse `NamedOptionDialog` (one button per option, no way out), as D-175 did for "choose one" of an effect; `Overlays.tsx` gains the purpose in the branch that already sends `option` and `effect` there. Wording, from `option-names.ts` (pure, unit tested): title "Damage replacement", prompt "3 damage from Goblin Chainwhirler would be dealt to you. Several effects apply. Choose which to apply first." (the damage source name, the amount, the recipient as "you" or the permanent's name); one button per choice with `text`, the permanent's name, and a second line "Then: 0 damage" or "Then: 3 damage to Ancient Adamantoise" from `then`. After the choice the engine asks again if two or more effects still apply and the order still matters (CR 616.1f). The log line (`game/describe.ts`, exhaustive switch) says "Alex applies Healing Salve first" for a new event `replacementChosen {seat, object, option}`, and "3 damage to Alex redirected to Ancient Adamantoise" for `damageRedirected`.

AI (`packages/ai/src/casual-options.ts`, `chooseOptionAnswer`; `GreedyAgent` and `HeuristicAgent` take the casual handler for `chooseOption`, `createCasualHandlers`, so one change covers the three):

- `CasualAgent` and `GreedyAgent`: the first option, which is the default order: prevent first. Legal, deterministic, and the owner's stated default.
- `HeuristicAgent`: among the choices, the one whose `then` is best for it: the least damage that lands on its own player or its creatures other than a creature that keeps damage and has room, then the one that prevents the most; ties go to the first option. It reads `then` only, so it needs no engine internals and stays inside the AI's rule (the engine's public API only). A first version may use the casual answer and leave this as a tuning step.
- `RandomLegalAgent`: picks uniformly among `d.options` through the generic `chooseOption` handler, legal by construction.

## 3. Pausing damage without breaking determinism or the log

`dealDamage` stays synchronous and never asks. A new pure `orderedDamage(state, events, answers)` simulates a batch of damage events in order on the immutable state (a scratch result that is discarded), feeding the known `answers` (one key per question, in the order the questions arise). It returns either `{ready: orders}` or `{question: <decision>}` for the first question without an answer. Only when it is `ready` is the damage dealt for real, by the existing `dealDamage` with the orders. Nothing is dealt, and no trigger is collected, before the last answer, so the pause is invisible to the rest of the engine (the problem D-157 found with a pause that collects triggers of events so far does not arise).

Callers that can pause:

- A resolving spell or ability (`dealDamage`, `dealDividedDamage`, fight, `dealDamageWithExcess`, all in `rules/effects.ts`, `rules/fight.ts`, `rules/damage.ts`): the instruction asks through `StepOutcome.needs` and stays at the head of the queue, as `chooseSacrifice` does; it carries the answers so far (`answers`) and runs again when the answer arrives. The events are the ones the effect would produce (all recipients, both fighters, the creature and the excess), so one instruction asks for all.
- Combat damage (`rules/combat-flow.ts`, `runDamageStep` and `answerDamage`): after the assignment is complete (automatic, or answered, CR 510.1), `orderedDamage` runs on the whole batch (CR 510.2: simultaneous). A question sets `pending` to the `replacement` decision with the plan in it (`resume: {step, assignments, answers}`, as the attack-tax decision carries `attacks`); the answer resumes `answerDamage`'s tail. Assignment is for the original recipients; the redirect happens as the damage is dealt (damage-redirection.md).
- The rider of a mana ability (damage that a mana ability deals to its controller, `rules/mana-abilities.ts`) cannot pause: mana abilities resolve inside a payment. It uses the default order and is recorded as a known limit (`docs/ROADMAP.md`). It matters only for a damaging mana ability together with a redirect and a shield on the same player.

Determinism and the log: the answer is a normal `chooseOption` action; `applyAction` is still the only mutation path; the decision id comes from the existing counter; the simulation is a pure function of the state and the answers, so replaying the action log asks the same questions in the same order and every answer in the log is checked against the recomputed legal options. The new events are `replacementChosen` and `damageRedirected` (`state/events.ts`; the web's exhaustive switch). Nothing uses time or randomness; the search order is fixed (default order, then key order). `ENGINE_VERSION` goes up because a replay with two non-commuting effects on one event now has an extra action.

## 4. Migrating D-156 and the tests

- Scope: only damage events change. The "would die" replacements, the enters-the-battlefield replacements and the counter replacements keep the fixed orders of D-156; they can use `damageModifiers`' shape (key, kind, default order, search, the `replacement` purpose with a different `event`) later without a new design. The implementation adds a new `D-` entry (the next number) that says damage events are lifted out of D-156, marks D-156's damage part superseded, and leaves its other parts in force.
- Code: `applyShields` is split: `applies` and the shield step become the building blocks of `damageModifiers` and `settleDamage`; the order "prevent all first, then numeric ones oldest first" becomes the default order. The file comment of `rules/prevention.ts` and `die-replacement.ts` are updated.
- Docs: the DEV-04 row of `docs/RULES_COVERAGE.md` (known deviations) and the 614, 616 row change from "on hold" to "damage: asked; others fixed"; `docs/ROADMAP.md` (the 616.1 bullets and the mana-ability limit); `docs/MECHANICS.md` (the new order step); `docs/ARCHITECTURE.md` (the new module).
- Tests that change: `scenario-xx-prevention.test.ts`, "two shields on one player: the older is used first (v1 order, CR 616.1)": two shields of different sizes now produce a question, and the test answers it both ways (the new assertion: either order is reachable); with two equal shields the test keeps its shape and asserts that no question is asked (the commuting case). Other prevention scenarios have one shield per event and do not change. The AI prevention games (`packages/ai/test/prevention-games.test.ts`, `casual-prevention.test.ts`) must keep passing with the new handler; the precon fingerprint of `tools/perf/precon-digest.ts` (D-173) must not change, which proves that no precon game asks (D-156 says no precon has two competing replacements).
- Tests added (scenario DSL, written first): zero or one effect asks nothing; two numeric shields of different sizes ask and each answer gives its result; two equal shields and two "prevent all" shields do not ask; a question per round (CR 616.1f) with three effects; the affected player is asked, not the source's controller (damage to an opponent's creature from your spell asks the opponent); an illegal answer is refused; the same log replays the same game; combat damage with a question; fight and excess damage with a question; the legal answers equal `options`; the web's pure prompt and rows; the AI answers (casual first option, heuristic by `then`, random legal) and a soak over a state with the effects.

## 5. Ancient Adamantoise

The card's text (the request export of 2026-10-29): "Vigilance, ward {3}", "Damage isn't removed from this creature during cleanup steps.", "All damage that would be dealt to you and other permanents you control is dealt to this creature instead.", and "When this creature dies, exile it and create ten tapped Treasure tokens." The redirect of the third line is one more modifier of kind `redirect` in `damageModifiers`, owned by the permanent with the ability (read from derived abilities, so losing abilities turns it off, CR 613.1f).

- It is the only effect: one applicable effect, no question; `settleDamage` applies it, the damage is dealt to the Adamantoise by the same source (CR 120.3: marked damage, deathtouch, wither or infect, lifelink of the source), and `damageRedirected` is emitted. The Adamantoise's own redirect does not apply to damage to itself ("other"), and the redirect is used once for this event (CR 614.5), so two Adamantoises do not loop. With two of them the final recipient depends on which redirect is applied first, so the affected player is asked which one applies.
- With a shield on the original recipient: two effects apply, the result depends on the order, the affected player is asked: "prevent the next 3 damage to you" first (the damage never happens) or the redirect first (the Adamantoise takes it, and a shield on the Adamantoise, if any, now applies, CR 616.2). The owner's default "prevent first" is the first option and what the AI gets.
- With a shield only on the Adamantoise and damage to you: the shield is not applicable to the original event; it becomes applicable after the redirect (CR 616.2). Only one effect is applicable at each step, so no question.
- Asker: the controller of the recipient at that step. For the Adamantoise, "you and other permanents you control" makes it the same player; a redirect to another player's creature is not in the slice (damage-redirection.md, "What it does not cover"), so a change of asker mid-process does not arise.
- `keepsDamage` (line 1) is independent of this proposal.

## 6. Size and steps

**Built (D-191):** steps 1 to 3 below. Differences from this design, all recorded in D-191: the field `then` of a choice is `outcome` (the lint rejects a property called `then`); the search is memoised on the result so far and also treats a default order that is at least as good as every other as "the order cannot matter" (so a shield for all damage with a numeric one never asks); a shield records no source, so a choice names its effect by what it does and only a static ability names its permanent; the exact search is `damageOrderMatters` and `settleDamage` is the loop of rounds that uses it; the combat plan travels in the decision (`DamageResume`) as designed; the question is `chooseOption`, purpose `replacement`; the events are `replacementChosen` (and `damageRedirected`, which belongs to step 4, is not built).


About 600 to 900 lines of engine code and tests together, plus about 200 in the web and the AI, over four reviewable steps, each a pull request that passes on its own:

1. Refactor with no behavior change: `damageModifiers`, `settleDamage` and the exact search, with the default order equal to today's `applyShields`; `dealDamage` uses it; the precon digest and the existing tests are unchanged. Unit tests of the search (commuting and non-commuting cases). No decision yet.
2. The question: the `replacement` purpose of `chooseOption`, `orderedDamage`, the pause in the effect path, combat and fight, the events, `legal-actions`, the testing DSL, `ENGINE_VERSION`, the new `D-` entry and the changed prevention tests.
3. The AI and the web: the casual handler (and the heuristic one), the dialog, the prompt and the log lines, with their tests and one end-to-end of the dialog.
4. The redirect itself and `keepsDamage` for Ancient Adamantoise (`damage-redirection.md`), the parser rules and the card's tests, on top of steps 1 to 3. Steps 1 to 3 have value alone: they make two shields ask today.

Risk: the pause in the effect path (the instruction stays at the head and runs again; a bug repeats damage) and in combat (`resume` data), both guarded by the rule that nothing is dealt before `ready`. The simulation doubles the damage work only when two or more effects apply.

## 7. Open questions for the owner

1. Skip the question when the order cannot matter (exact search, recommended), or always ask when two or more effects apply (simplest, exactly the letter of CR 616.1, but it asks about two Fogs)? Recommendation: skip when every order gives the same result.
2. Show "Then: ..." on each button (the result if the rest follow the default order)? Recommendation: yes; it is what makes the question answerable without bookkeeping.
3. The AI's choice: the first option (prevent first) for all agents in the first version, or the heuristic agent choosing by `then`? Recommendation: casual and greedy take the first option; the heuristic takes the least damage to itself, ties to the first option.
4. The rider of a mana ability cannot ask; it takes the default order and stays a documented limit. Recommendation: accept, record in `docs/ROADMAP.md`.
5. Pause scope: asking before anything is dealt (simulate, then deal) means the questions of a combat damage batch are all asked first, in the order of the assignments, and answered for a state that does not yet include the earlier damage of the batch. Recommendation: accept; it keeps the batch simultaneous (CR 510.2) and avoids collecting triggers in the middle of it. The cost is that a later event's question is shown with the default answers of the earlier ones already applied in the simulation, which is correct because the earlier ones are answered first.
6. Move the "would die" replacements to the same decision (a later slice, own proposal) or leave them under D-156? Recommendation: leave them; no supported card has two that compete, and the Adamantoise slice should not carry it.
7. Does a redirect to another player's creature (not in the slice) ever matter? Recommendation: no; keep it refused, so the affected player never changes in the middle of the process.
